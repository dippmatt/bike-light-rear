# The light derives a cloned AirTag's rotating keys itself, on a counter that may lag but never lead

ADR-0011 sent one fixed key. To appear in Apple's Find My app the light instead sends the keys of a real AirTag (accessory data taken from the owner's Apple account), which change every 15 minutes. A first version precomputed a week of keys on the host and compiled them in (`gen_airtag_table.py`, 18 kB, counted from boot): it went stale after a week, restarted at the first key on every reset and needed a reflash. The light now runs the AirTag's own key schedule. It has no real-time clock and gets none in the next hardware revision.

- **The schedule is an index, not a time.** Key *i* follows from key *i-1* by a hash (`SK_i = X9.63-KDF(SK_{i-1}, "update")`); the advert is x(P_i) with `P_i = u·P0 + v·G` on P-224, u and v from `X9.63-KDF(SK_i, "diversify")` (`findmy_keys.c`, same algorithm as FindMy.py). The light needs the index only to know which key is next, not the date.
- **Lag is fine, lead is not.** A real AirTag has no battery-backed clock either. Apple's side keeps the last index it saw and when (`lastIndexObserved`, `lastIndexObservationDate`; FindMy.py: `alignment_index/date`) and searches from there up to "one step per 15 minutes since". A tag that fell behind (battery out, slow clock) is still found and re-aligns the search; a tag that runs ahead of wall-clock time sends keys nobody asks for yet. So the light rotates every `HAYSTACK_ROTATE_MS`, 0.1 % longer than 15 min, which covers the RC clock's error (ADR-0006), and resumes at its last stored index after a reset. Rejected: a time source (BLE Current Time Service needs a BLE stack, ADR-0011; ANT+ common page 83 depends on the bike computer; a 32 kHz crystal or RTC chip is a board change), because none is needed for lag-only operation.
- **Public master key only.** The provision block holds P0 = d0·G, not d0 (`tools/haystack/provision_airtag.py` computes it). Read-out flash lets someone predict the light's future adverts, but never decrypt the location reports. After each rotation the old SK is overwritten in RAM; older ones stay in the flash log until its page is erased (about a day).
- **Flash log through the SoftDevice.** Three pages at `KEY_STORE_ADDR` (0x7D000), outside the image: a provision block that only the host writes, and two log pages of 48-byte records `{index, SK}` (85 per page), appended at each rotation through `sd_flash_write` and erased in turn when one is full (`key_store.c`). About one erase per page every 42 h, decades at 10 000 cycles. Each record carries a CRC and the provision block's CRC as a tag, so torn writes and records of an earlier provisioning are skipped. A save that fails is retried every `HAYSTACK_POLL_MS`; if the light resets before it lands, it repeats one key, which only adds lag.
- **Provisioning = resync.** `make flash-keys` computes the current index from the accessory JSON on the host and writes the provision block and blank log pages. `make flash` (chip erase) runs it too. It is also the cure if the light lagged too far, for example after weeks with a flat battery: how far Apple's search reaches behind its last observation is not documented.
- **Cost.** micro-ecc (P-224 only) and tinycrypt SHA-256 add about 6 kB of flash; the table was 18 kB. The derivation runs in the main loop, never in the timeslot callback, once per rotation; its time is in `haystack_stats.derive_ms`: 177 ms measured on the rear (`-Os`). The main loop is blocked that long once every 15 min; ANT runs at SoftDevice priority and is unaffected.
- **Rotation is checked on its own timer.** `haystack_poll()` runs from `ST_HAYSTACK` every 10 s, not from SoftDevice events, which are rare in Deep Sleep with the ANT channel closed.
- **Open risks.** (1) Only the primary key chain is sent. A real AirTag away from its owner switches to the secondary chain (daily keys); whether Apple keeps looking up the primary keys of a "separated" tag for long periods is unknown. (2) The real AirTag, if still in use, sends the same keys; its reports and the light's are indistinguishable. (3) Flash writes during the front light's proximity search and over long Deep Sleep are not yet measured. (4) Like ADR-0011, all of this relies on the unofficial route to Apple's network.
- **Bench result (rear, 12 Nov 2026, ANT channel open).** Shown in the Find My app. One derivation 177 ms; the advert kept its 2 s rhythm through it, with no blocked or overrun slots. Every rotation's record landed (`flash_errors` 0, no skipped slots). Page change tested by pre-filling the log with older-index records: the full page was erased (filler gone) and the log continued there. After resets the light resumed at the newest record, also with 168 older records present, and sent FindMy.py's key for that index byte for byte. Each reset restarts the rotation timer, so the light ended 1 index behind Apple's newest, as intended.

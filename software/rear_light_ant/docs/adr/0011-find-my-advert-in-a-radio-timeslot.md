# The light sends a Find My advert from a radio timeslot on the ANT-only SoftDevice

The rider wants to find a lost or stolen light through Apple's Find My network. That needs a BLE advertisement in the Find My format (the community "OpenHaystack" format); the light itself never connects to anything. The firmware runs on S212, which has no BLE, and ADR-0005 left BLE out on purpose.

- **Raw packet in a Radio Timeslot, not a BLE stack.** S212 supports the Radio Timeslot API next to the ANT stack (S212 SDS section 9.2). The advert is one fixed non-connectable packet (ADV_NONCONN_IND) that `haystack.c` sends on channels 37, 38 and 39 with the RADIO registers, once per 2 s, at the lowest timeslot priority. A timeslot is about 2.4 ms, and the SoftDevice scheduler places it between ANT events; a collision is resolved by priority, and the advert (lowest priority) gives way. Moving to S340 (ANT and BLE) was rejected: 200 kB flash and 8 kB RAM instead of 72 kB and 3 kB, a new SoftDevice API, a moved application start, and BLE host code for a packet that is a constant (PORT_DECISION option C).
- **Fixed key, no rotation.** The advert carries one 28-byte key per light. It is the simplest thing that works with the existing tools (`generate_keys.py`, FindMy.py) and needs no flash storage, which this firmware does not have. The price: the light is recognisable to anyone who reads the advert, and iPhones can show an unknown-tracker alert if the light travels with a stranger. Rotating keys would need persistent state and a different back end; not done. *Superseded for AirTag builds by ADR-0012* (rotating keys from a flash key store); the fixed key remains the `HAYSTACK_KEY_<LIGHT>` option.
- **Always on, also in Deep Sleep.** The advert is not tied to the state machine. Deep Sleep is System ON idle with the SoftDevice running (ADR-0004), so the timeslot keeps firing: a parked or stolen light stays findable, which is most of the point. The cost is a few microamperes on average (estimate, not measured) on top of the unmeasured T12 budget. `HAYSTACK_INTERVAL_MS` in `config.h` is the knob.
- **Optional at build time.** The advert exists only if `keys.local.mk` has a key for the variant (`HAYSTACK_KEY_REAR`, `HAYSTACK_KEY_FRONT`). Without it the image is byte-identical to before. A failure to start the timeslot session is recorded (`last_error` site 0x34) and does not stop the light or ANT.
- **Not authenticated, not a control path.** The advert only identifies the light. No command can arrive over it, so ADR-0001 is unaffected.
- **Open risks, to measure on the bench.** (1) The front light's proximity search holds the radio for long stretches and may starve timeslots (`haystack_stats.blocked`, `adverts`). (2) The RC low-frequency clock (ADR-0006) is only used for scheduling here; an advert that is a few hundred ppm off in time is harmless, but the ANT risk of ADR-0006 is unchanged. (3) Whether a stock iPhone reports this advert in the real world is only proven by getting a position from `track.py fetch` (tools/haystack/README.md).
- **Bench findings (rear, S212 7.0.1, ANT channel open).** Two things the SDS does not say. (1) The RADIO is powered down between ANT events and is not powered up for a timeslot: register writes were lost until `haystack.c` power-cycled it (`POWER` 0, then 1) at the slot start and restored the old state at its end. (2) The RADIO interrupt is left disabled in the NVIC during the timeslot while TIMER0's is enabled, so the code enables it itself (allowed: the signal handler runs at the SoftDevice's own level). With both fixes and the normal (lowest) priority, one advert goes out about every 2.1 s with ANT at 8.1 events/s unchanged, also with the ANT channel closed in Deep Sleep: 23 adverts in 44 s, 1 to 2 cancelled slots in a minute, all recovered by the retry. Measured with the counters in `haystack_stats`, not yet seen on air.
